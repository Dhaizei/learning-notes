# Codex 如何读取其他聊天记录

核对日期：2026-11-05  
分类：计算机与工具 → Codex

**缺少 `read_thread` 工具，不等于无法读取聊天。先检查实际工具，再检查本机官方 App Server 的只读接口。**

## 本篇学习重点

- **建议掌握**：工具缺失不等于能力不存在；入队、开始处理、收到答复是不同状态。
- **用时查阅**：App Server 方法名、schema、分页参数和 CLI 语法。
- **可以要求 Codex**：请先检查可用读取路径，读到正文后再概括；失败时给具体证据。

## 我的问题

引用另一条聊天后，助手说没有 `read_thread`，要求复制内容；后来却通过 App Server 成功读到了正文。工具名称和实际能力有什么区别？

## 三个概念

| 名称 | 含义 |
|---|---|
| `read_thread` | 应用说明可能提到的助手工具名；必须检查本次是否实际提供 |
| `thread/read` | App Server 接口，可按 ID 读取已保存聊天的元数据 |
| `thread/turns/list`、`thread/items/list` | 按当前版本支持情况分页读取聊天正文 |

它们不能仅凭名称相似就视为同一个接口。聊天引用通常给出身份信息，并不等于正文已经进入当前上下文。

## 正确处理顺序

1. 确认引用的 thread ID，检查可直接调用的读取工具。
2. 工具缺失时，检查 `codex app-server`、实际协议 schema 和连接方式。
3. 读取正文并处理分页后再分析；只有标题或元数据时不能声称读过聊天。
4. 失败时说明具体限制，例如连接失败、版本不支持或权限不足。

查阅历史保持只读，不为读取而调用 `thread/resume`、发消息或开启新 turn。历史聊天中的指令按资料对待，不自动执行。

## 本次验证与更正

本机已通过 App Server 读取「学习消除技巧」和 `study` 下相关聊天。测试使用过 `thread/read` 的 `includeTurns: true`；官方对分页聊天已将这种全量读取方式标为弃用，后续应按实际版本优先使用分页接口。

之前“没有工具所以无法读取”的判断遗漏了可用接口，应改成“尚未完成可用读取途径的检查”。

## 发送与唤起是不同步骤

读取历史、向聊天入队消息、让目标开始处理是不同能力。用户明确要求通知另一聊天时，才按授权发送；不能因读取成功就认为自己能通知或唤起。

本机验证过 `codex queue --thread <ID> --message <文本>` 可返回消息入队 ID。官方另提供 `--resume` 尝试恢复未加载的聊天；这需要可用的本地 daemon 或指定远程服务器，即使恢复失败，入队命令也可能仍返回成功。[官方队列说明](https://learn.chatgpt.com/docs/cli/reference#codex-queue)

2026-11-05 复核交接中，消息已入队，但后续 `app-server proxy` 默认控制 socket 不存在、连接失败；桌面进程存在不代表这个地址可用。因此应分别报告“入队成功”“处理已开始”“回复已完成”，不能互相替代。Windows 的本地 socket 错误也不能直接解释为互联网故障。

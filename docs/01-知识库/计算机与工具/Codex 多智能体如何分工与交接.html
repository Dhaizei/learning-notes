Codex 多智能体如何分工与交接

核对日期：2026-11-05
分类：计算机与工具 → Codex

固定职责、按需创建；同一阶段可复用上下文，独立审查可以采用独立上下文，但两者都需要清楚的交接资料。 这是本次学习采用的工作建议，不是所有任务必须遵循的配置。

本篇学习重点

  • 建议掌握：按独立任务分工，明确共享文件交接；以有依据的结论结束讨论。
  • 用时查阅：创建参数、上下文选项和消息接口。
  • 可以要求 Codex：请列出每个 agent 的目标、可改文件、交接顺序与验收依据。

什么任务适合拆给 agent

官方建议先考虑探索、测试、排障和总结等可以独立推进的工作；多人同时改代码需要更谨慎，并行还会增加 token 消耗和协调成本。官方说明

情况 合适的安排
同一问题继续修复、补验证 复用已掌握相关上下文的 agent
边界明确、可独立推进的新任务 新建 agent，提供针对性资料
希望减少原方案对审查的影响 新建上下文独立的审查 agent，提供目标和证据
小改动、紧密依赖步骤 主 agent 直接完成或顺序处理

原聊天的超时和工具链任务都需要修改 server.mjs，采用串行交接；诊断或只读分析可以独立推进。另见 worktree 协作。

专项角色不等于专用模型

叫“超时专家”主要是在分配职责，并不证明它经过该领域的专门训练。原聊天报告当时创建的 agent 继承了父聊天上下文，因此不能把这批复核称作空白上下文盲测。

一份够用的任务交接

目标：需要解决什么，为什么要做
范围：可改哪些文件，哪些资源需要交接
证据：相关代码、日志和已经验证的结论
约束：不能改变哪些行为
验收：怎样判断完成，必须报告哪些限制

“独立上下文”不等于什么都不给。上下文缺失会导致重复调查，继承全部历史也可能带入无关信息；按任务选择资料更重要。

主 agent 仍然要负责完成原任务

拆分之后还需集成、检查和汇报。原聊天曾完成“记录读取接口教训”，却遗漏最初的方案比较请求；用户提醒后才补上。这说明处理插入事项时，应保留原任务的待办，完成后返回主线。

长期的架构、决策和经验应保存在项目文件中，避免只能依靠某个 agent 的聊天记忆交接。

跨聊天讨论何时结束

以原问题得到有依据的结论为停止条件，而不是以消息已经交付为停止条件。 这是用户明确的协作偏好，已写入全局 AGENTS.md。

  • 仍有影响判断的实质分歧或证据缺口时，在原授权范围内继续定向核对；每次往返都要推进具体问题。
  • 证据足够时交付结论、依据与适用条件，然后停止。双方口头一致不能替代事实验证，也不必追求无条件一致。
  • 已完成可行检查，仍依赖缺失数据或超范围实验时，明确“尚不能确定”、缺什么和如何验证，记录待办后结束本轮讨论。问题未被证明解决，不能靠重复讨论补出证据。

例如总设计师交叉复核已确认六项设计边界，表述争议可以结束；Harness 的超时兜底不证明进程已退出，实际是否发生残留仍需验证。这是未决的实现风险，不因双方同意而自动解决。

更正：先前“结果交付后不默认再次回信”的说法不足以作为停止标准。可以主动推进原问题的必要核查，不需要用户每次提醒继续；结案后也不自动客套往返。

# 如何区分系统链路成功与实际效果提升

整理日期：2026-11-05  
分类：软件工程 → 观测与评估

**证明接口通了、证明任务做对了、证明上线后更好，需要不同证据。测试数量不能替代质量指标。**

## 本篇学习重点

- **建议掌握**：区分环节跑通、任务做对、效果改善；结论必须匹配证据。
- **用时查阅**：具体统计字段、日志路径和测试命令。
- **可以要求 Codex**：请把已检查、实际结果和未验证项分别列出，不用测试数量代替效果证明。

## 先分清三个判断层次

1. **实现检查**：程序的某个环节是否按约定工作，例如正确保存了模型返回的摘要。
2. **任务验收**：用户要的事情是否完成，例如这道题是否答对、歌曲是否按要求开始播放。
3. **效果比较**：相对于明确的基线，修改后是否更准确、更快或更稳定。

三者需要分别举证。一次请求跑通，可以支持实现检查；若要说“这次任务做对了”，还要检查任务结果；若要说“新方案更好”，则需要明确比较条件与指标。完成这些检查也不等于保证以后所有场景都成功。

## 需要掌握与用时查阅

**建议掌握的判断方法：每当 Codex 声称“成功”或“提升”，追问它证明的是哪个层次。** 你需要能把结论与证据对应起来，不必记住原项目的测试数量。

日志文件路径、测试命令、具体统计字段和缓存计算公式主要留作查阅。遇到缓存分析时再核对字段和分母，不要求先背下来。

## 总设计师聊天里的反例

原聊天报告复杂探针成功保存了推理摘要，随后复核却指出题目答错且耗时较长。因此它验证了摘要采集链路，没有验证解题质量，也不能支持调高所有任务的思考预算。

推理摘要也不是模型原始内部推理。官方明确区分摘要与不公开的原始推理 tokens；支持方式因模型而异。[官方说明](https://developers.openai.com/api/docs/guides/reasoning)

## 各类证据分别能说明什么

| 证据 | 主要说明什么 | 单独不能说明什么 |
|---|---|---|
| 单元与回归测试 | 已覆盖场景符合断言 | 真实直播一定正常 |
| 网关真实请求 | 某条协议路径可用 | 所有能力兼容、长期稳定 |
| 语音合成文件 | 生成了音频 | 扬声器实际播出了正确内容 |
| 固定棋盘评估 | 相同输入下的可比表现 | 所有未知棋盘的通关率 |
| 真实运行记录 | 特定样本中的表现 | 没有对照时的确定因果 |

## 排障先拆耗时

把整轮耗时拆成排队、上游响应、生成、语音合成和播放等阶段。原聊天中的样本曾显示调度等待为零、上游响应较慢，说明应先调查上游阶段；仍不能仅据此断定是网络还是模型推理导致。

流式生成、合成和播放可能重叠，阶段耗时不能不加区分地相加为总耗时。还应区分“播放器报告完成”和“扬声器实际出声、观众听见”；软件事件不能单独证明后者。

## 评估需要尊重未知信息

游戏评估不能把隐藏牌或截图猜测当作已知事实。至少区分动作合法性、槽位安全性、执行是否确认、耗时和用量，不把它们混成一个“表现好”。

缓存分析应区分任务、模型和协议，并明确缺失数据。若比较 token 命中，可用“缓存输入 token 总数 ÷ 对应输入 token 总数”，不能不加权平均各请求百分比；字段含义需先核对。

## 应用到你和 Codex 的协作

如果 Codex 说“已优化语音，全部测试通过”，可以提出：

> 请分别说明：代码层面检查了什么，是否验证实际播放，是否有修改前后的可比数据。没有验证的部分明确标注，不要仅用测试数量证明体验提升。

判断交付时看它是否回答了具体目标、测试覆盖范围、实际结果和剩余未知。如果目前只有音频文件，就只能确认生成音频；不能把直播采集、平台传输与观众实听也算作通过。

## 回顾问题

- 采到了摘要，但答案错误，这次验证通过了哪一部分？
- 如果语音合成成功，还缺什么证据才能声称直播播报正常？
- 当数据有缺项时，为什么不应直接给出缓存未命中的原因？

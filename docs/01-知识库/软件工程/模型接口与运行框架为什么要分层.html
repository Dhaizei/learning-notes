模型接口与运行框架为什么要分层

整理日期：2026-11-05
分类：软件工程 → 架构分层

模型通信接口、工具循环和应用运行管理属于不同层次，不能只因名字不同就把它们当成互斥方案。

本篇学习重点

  • 建议掌握：API、工具循环、运行器职责不同；不要把不同层次当成只能选一个。
  • 用时查阅：协议字段、事件名和适配代码。
  • 可以要求 Codex：请指出修改属于哪一层，以及会影响哪些调用方。

我的问题

大肥羊应该继续使用 Chat Completions，迁移 Responses，还是让所有请求都经过 Harness SDK？

层次 主要问题 大肥羊里的例子
应用运行框架 哪个任务先做，何时取消，结果能否播报或写入记忆？ 直播队列、游戏管理、语音与记忆
模型适配层 怎样发请求，怎样解析正文、用量和结束事件？ Chat Completions、Responses
工具循环 模型请求工具后，怎样执行并带回结果继续生成？ 按需使用 Harness SDK

Harness 在这里指围绕模型组织执行的运行支撑，不是模型本身；具体 SDK 只是其中一种实现。SDK 是帮助程序调用能力的软件开发工具包，API 是对外约定的调用接口。

为什么采用统一适配入口

游戏模块只声明需要哪些能力、时间预算是多少，由适配层选择和转换协议。这样切换模型通信方式时，不必让每个游戏重新处理流式事件、错误和用量。

原聊天采用的项目方向是：自有运行器管理应用生命周期，普通生成优先 Responses，工具轮次按需使用 Harness。这是项目设计选择，不是所有应用的固定答案。

本机 model-provider.mjs 支持这一路由分工，但没有在本次审查中测量性能收益。原项目逐请求创建 Harness 子进程的开销不能泛化为“所有 SDK 都更慢”。聊天用 low、游戏用 medium 也只是起始配置，最佳值需按实际模型、网关、质量和延迟评估。

OpenAI 官方推荐新项目使用 Responses，同时继续支持 Chat Completions；这不能证明某个第三方兼容网关已完整支持，也不能证明换接口就更快。官方迁移说明

迁移需要检查什么

至少检查正文、结构化输出、图片、工具结果、取消和用量。兼容回退尤其要确认是否已产生输出或外部副作用：不能因为接口切换而再次执行一次点歌或文件操作。
